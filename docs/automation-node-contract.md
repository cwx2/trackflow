# TrackFlow 自动化节点、数据流与批处理契约

> **定位**：这是自动化工作流所有节点的共同基座。新节点、编辑器交互、校验器、执行引擎、模板和执行日志都必须遵守本文。  
> **配套文档**：[工作流编辑器架构设计](workflow-editor-design.md)。本文补齐该文档未定义的端口有效性、集合处理、失败策略和可观测性语义。  
> **状态**：目标契约；新增功能必须直接遵守，禁止以接受未知字段或前端补丁的方式绕过契约。

---

## 1. 目标

用户配置工作流时，应当像观察水流一样理解数据：数据从一个节点的输出流入下游节点的输入；集合数据可以逐条流过后续链路；每一条数据的成功、失败、重试和去向都清晰可见。

系统必须同时做到：

1. **易用**：用户无需先理解数组、循环、引用或 JSON，正常连线即可完成常见自动化。
2. **确定**：保存的定义完整表达运行语义；不能依赖前端临时状态、隐式默认值或不受控的“猜测”。
3. **安全**：写操作、外部请求和脚本执行需要明确确认、限流、幂等和失败处置。
4. **可观测**：能够回答“哪一条数据在哪个节点失败、重试了几次、最后去了哪里”。
5. **可演进**：节点能力可扩展，但工作流定义只包含受支持的正式字段。

---

## 2. 核心原则

### 2.1 端口是运行契约，不是纯 UI

输入端口决定节点在什么条件下可运行；输出端口决定节点会产生什么数据。端口名称、数据类型、基数和绑定方式都是可保存、可验证、可执行的契约。

### 2.2 用户看到“自动逐条处理”，系统保存“明确批处理语义”

数组输出连接到单条输入时，编辑器可以自动创建批处理段，但不得把遍历藏成不可检查的黑盒。保存后的定义和执行日志必须记录：来源、并发度、失败策略、聚合结果和每一项的状态。

### 2.3 只校验本次真正生效的输入

可选输入、默认输入和因配置关闭的输入不能被当作错误。只有“**已启用且必填**”的输入未满足时，才阻止保存、发布或运行。

### 2.4 默认安全，逐步暴露复杂度

默认串行、失败记录并继续、有限重试、最小日志摘要。并发、失败即停、死信、补偿子流程等能力在高级设置中提供，不要求普通用户一开始理解。

### 2.5 连线必须有数据含义

一条边始终代表一个输出端口到一个输入端口的绑定。不能使用无端口的“装饰性连线”，也不能让一条输入同时保留多个有效来源。

---

## 3. 术语

| 术语 | 定义 |
|---|---|
| 端口（Port） | 节点的具名输入或输出数据接口。 |
| 基数（Cardinality） | 数据是单值 `single` 还是集合 `collection`。 |
| 绑定（Binding） | 输入取值方式：固定值、上游引用或模板表达式。 |
| 有效端口 | 在当前节点配置和运行上下文下实际参与执行的端口。 |
| 批处理段（Batch scope） | 将一个集合的每个元素分别送入下游链路的运行范围。 |
| 项（Item） | 批处理中的单个元素，例如一条工单。 |
| 异常分支 | 接收失败项、跳过项或重试耗尽项的显式下游路径。 |
| 死信（Dead letter） | 无法自动完成、但需要保留以供人工或后续重投的项。 |

## 4. 节点契约

每种节点必须在后端注册唯一的 `NodeContract`；前端只展示和编辑后端声明的能力。前端定义可用于渲染，但不得成为另一份独立真相来源。

### 4.1 节点级契约

```ts
type NodeContract = {
  type: string
  meta: {
    title: string
    icon: string
    color: string
    description: string
  }
  inputs: InputPortContract[]
  outputs: OutputPortContract[]
  runtime: RuntimePolicy
  observability: ObservabilityPolicy
}

type RuntimePolicy = {
  testMode: 'safe' | 'confirm' | 'simulated'
  retrySafe: boolean
  defaultMaxAttempts: number
  idempotency: 'none' | 'recommended' | 'required'
}
```

`meta` 只允许 `title`、`icon`、`color`、`description` 四个字段。分类属于节点库展示信息，不属于持久化的 `nodeMeta`；任何未知字段必须在保存前被拒绝，而不是被静默忽略。

### 4.2 输入端口契约

```ts
type InputPortContract = {
  name: string
  label: string
  valueType: 'string' | 'number' | 'boolean' | 'object' | 'array' | 'any'
  cardinality: 'single' | 'collection'
  semanticType?: 'issue' | 'issueId' | 'issueKey' | 'markdown' | 'comment' | 'json'
  bindingModes: Array<'literal' | 'ref' | 'template'>
  required: boolean
  defaultValue?: unknown
  enabledWhen?: Expression
  requiredWhen?: Expression
  description?: string
  sensitive?: boolean
}
```

端口状态计算规则：

| 状态 | 条件 | 运行行为 |
|---|---|---|
| 禁用 | `enabledWhen` 为假 | 不展示为缺失、不传给执行器。 |
| 默认值 | 已启用、未绑定、有 `defaultValue` | 使用默认值。 |
| 可选未绑定 | 已启用、非必填、无默认值 | 以 `null`/缺省值运行。 |
| 待满足 | 已启用且 `requiredWhen`/`required` 为真、又无有效绑定 | 阻止运行。 |
| 已满足 | 固定值、合法引用或合法模板存在 | 将解析值传给执行器。 |

`requiredWhen` 和 `enabledWhen` 必须只依赖节点自身配置、开始输入或已确定的上游数据；不得依赖下游状态。

### 4.3 输出端口契约

```ts
type OutputPortContract = {
  name: string
  label: string
  valueType: 'string' | 'number' | 'boolean' | 'object' | 'array' | 'any'
  cardinality: 'single' | 'collection'
  semanticType?: string
  producedWhen?: Expression
  retention: 'summary' | 'full' | 'sensitive'
  description?: string
}
```

- 输出未被下游消费是**信息提示**，不是结构错误；副作用节点即使输出无人使用也可以合法运行。
- `producedWhen` 为假的端口不应被标成“缺失”；运行日志应显示为“本次未产生”。
- `retention` 控制日志展示和持久化脱敏策略，不改变节点执行结果。

### 4.4 绑定模型

```json
{ "type": "literal", "value": 20 }
{ "type": "ref", "nodeId": "search-1", "outputName": "issues" }
{ "type": "ref", "nodeId": "item", "outputName": "value", "path": "id" }
{ "type": "template", "template": "处理 {{context.markdown}}" }
```

一个输入端口在同一次执行中只能有一个有效绑定。用户重新连线时，编辑器必须替换旧引用并清楚提示；不允许多个来源以未定义顺序覆盖。

## 5. 数据类型、语义类型与自动映射

### 5.1 双层兼容性

连线前必须同时判断：

1. **数据类型兼容**：`string → string`、`object → object`；`any` 可兼容任何类型。
2. **语义类型兼容**：`issue → issue` 优于普通 `object → object`；`issueId → issueId` 优于普通 `number → number`。

数据类型兼容但语义不完全相同，可以允许连接并显示黄色提示；数据类型不兼容时禁止直接连线。

### 5.2 字段投影

对象不能直接接到 `issueId`/`string` 等单值输入。若对象存在已声明字段，可在连线时提供字段选择：

```text
当前项（工单对象） → 获取需求.工单 ID / 编号
可选：id（推荐） / key
```

保存时必须写成带 `path` 的引用；不得仅凭端口标题猜测字段。

### 5.3 推荐映射

编辑器可根据语义类型、名称和当前作用域推荐绑定，但必须由用户确认以下有副作用或存在歧义的映射：

- 多个候选输出都兼容；
- 需要字段投影；
- 需要将集合转为逐条处理；
- 需要覆盖已有输入绑定。

## 6. 集合数据与批处理

### 6.1 用户体验

当用户将 `collection` 输出拖到 `single` 输入，编辑器不应只报“类型不匹配”。应展示轻量决策：

```text
“需求列表”包含多条数据，而“工单对象”每次只接收一条。

[逐条处理（推荐）]  自动创建批处理段
[整批传入]            仅目标支持集合时可用
[取消]
```

选择“逐条处理”后，画布显示可折叠的批处理段，而非要求用户手动添加循环节点。展开时可看到 `当前项`、成功、失败、跳过和汇总端口。

### 6.2 持久化模型

批处理不是前端动画，应保存为正式结构：

```ts
type BatchPolicy = {
  source: { nodeId: string; outputName: string; path?: string }
  mode: 'serial' | 'parallel'
  concurrency: number
  maxItems?: number
  itemVariable: 'item'
  onItemFailure: 'continue' | 'stop' | 'route'
  retry: RetryPolicy
  deadLetter?: DeadLetterPolicy
}

type RetryPolicy = {
  maxAttempts: number
  backoff: 'none' | 'fixed' | 'exponential'
  initialDelaySeconds?: number
  maxDelaySeconds?: number
  retryOn?: Array<'network' | 'timeout' | 'rate_limit' | 'transient'>
}
```

实现可将批处理编译为内部的 `map`/`batch` 执行节点，但保存和日志必须保留可读的批处理语义和稳定 ID。

### 6.3 默认策略

| 配置 | 默认值 | 原因 |
|---|---:|---|
| 模式 | 串行 | 保护外部服务与写操作顺序。 |
| 并发数 | 1 | 用户显式调大后才并行。 |
| 最大项目数 | 节点结果上限 | 防止一次触发无限处理。 |
| 单项失败 | 记录并继续 | 一条脏数据不阻塞其他项。 |
| 自动重试 | 读取节点 2 次；写节点 0 次 | 不重复产生副作用。 |
| 重试耗尽 | 路由失败项 | 让用户定义补偿处理。 |

### 6.4 批处理输出

批处理段固定提供：

```text
successItems   成功项数组
failedItems    失败项数组（含错误、尝试次数、最后输入摘要）
skippedItems   跳过项数组
summary        { total, succeeded, failed, skipped, durationMs }
```

下游可以把 `failedItems` 接到人工审批、通知、创建异常工单或补偿子工作流。`summary` 可用于条件判断和最终报告。

### 6.5 并发与顺序

- 串行模式按来源数组顺序执行。
- 并行模式不保证完成顺序；每个项必须保留 `index` 和稳定项标识。
- 输出数组默认按来源顺序聚合，而不是按完成时间聚合。
- 取消工作流后，不再领取新项；已开始项依照节点取消策略收尾。

## 7. 失败、重试与补偿

### 7.1 失败策略的层级

1. **节点策略**：节点契约声明能否安全重试、默认次数和幂等要求。
2. **批处理策略**：用户定义单项失败如何影响其他项。
3. **工作流策略**：用户定义最终失败时如何通知、审批、停止或补偿。

用户配置不能突破节点安全边界。例如“添加评论”默认不可自动重试；只有提供幂等键或后端确认幂等后，才可开启重试。

### 7.2 异常分支

失败不是终点，应有可连线的正式出口：

```text
正常输出 ──→ 后续处理
失败项   ──→ 通知负责人 / 人工审批 / 补偿子流程 / 死信
```

若用户未连接失败出口，系统仍保存失败日志并将批处理标记为“部分失败”；发布前提示但不强制阻断，除非工作流被标记为“必须全成功”。

### 7.3 死信与重投

死信记录至少包含工作流版本、批处理 ID、项标识、最后输入摘要、错误分类、尝试次数、失败时间和建议动作。用户可在管理页执行：

- 重试单项；
- 重试所有同类失败项；
- 修改后重新投递；
- 关闭并标记为已人工处理。

重投必须创建新的尝试记录，不能覆盖原始失败证据。

## 8. 编辑器交互规范

### 8.1 端口视觉状态

| 视觉 | 语义 |
|---|---|
| 红色实心输入端点 | 启用且必填，但当前未满足。 |
| 蓝色空心输入端点 | 可连接、尚未绑定。 |
| 绿色连接态 | 当前输入已绑定并会参与运行。 |
| 灰色端口 | 当前配置禁用，不参与运行。 |
| 橙色输出端点 | 可作为下游数据来源。 |
| 输出消费计数 | `· 0` 表示未消费，`· 2` 表示被两个下游使用。 |

端点命中区必须大于视觉圆点，鼠标进入时放大并高亮可连接目标；连线完成后线端与端点严丝合缝。

### 8.2 连线反馈

- 拖动时只高亮兼容目标；
- 类型不兼容时给出原因和可选转换/批处理建议；
- 覆盖已有输入绑定前明确说明来源将被替换；
- 成功连接后，在配置面板显示“来自：节点.输出”，并提供一键断开；
- 不要让用户同时在连线和输入框内维护两份来源。

### 8.3 节点配置面板

配置面板按“本次会用到的数据”组织：

1. **运行约束**：安全试运行、真实执行需确认、可重试次数。
2. **必需输入**：只展示当前启用且必填的端口。
3. **可选输入**：折叠展示，说明默认行为。
4. **高级选项**：超时、限流、批处理、错误处理。
5. **数据血缘**：每个有效输入来源、每个输出的消费方。

不要用“所有端口都摆在页面上”代替清晰的运行语义。

### 8.4 节点测试

- `safe`：可以直接试运行；若上游引用不存在，列出需要模拟的字段并生成 JSON 示例。
- `confirm`：展示将产生的真实副作用，必须显式勾选确认。
- `simulated`：明确标注为模拟，禁止伪装成真实执行结果。

测试结果自动进入节点调试面板：摘要、输入、输出、原始数据和时间线分层展示；大对象使用摘要与按需展开，不应塞满画布。

## 9. 执行可观测性

### 9.1 三层日志

| 层级 | 必须回答的问题 |
|---|---|
| 工作流 | 是否完成、总耗时、总输入、总输出、成功/失败/跳过数量。 |
| 批处理 | 已处理/总数、当前并发、成功/失败/重试/跳过数量。 |
| 单项与节点 | 某一项在哪个节点失败、输入摘要、输出摘要、耗时、错误和尝试历史。 |

SSE 至少推送：`workflow_started`、`batch_progress`、`item_started`、`node_running`、`node_succeeded`、`node_failed`、`item_retrying`、`item_completed`、`workflow_completed`。

### 9.2 数据血缘

每条执行记录应保留：

- 输入端口最终使用的绑定来源；
- 值的摘要、类型、脱敏状态；
- 输出被哪些下游节点消费；
- 批处理项的来源索引与稳定业务标识；
- 定义版本和节点契约版本。

敏感字段只存掩码、哈希或授权后的加密快照；日志 UI 默认不展示完整密钥、令牌、密码、Cookie 或个人隐私内容。

### 9.3 运行动画

运行时，只有在下游节点实际获得数据并开始处理时，才沿已选中的边播放流动动画。动画是执行事件的投影，不能用前端定时器伪造成功。

- 正常数据：主题色流动；
- 重试：橙色回流；
- 异常分支：红色流动；
- 跳过：灰色淡出；
- 批处理：边上显示实时计数，如 `12 / 20`。

## 10. 校验、诊断与发布门槛

### 10.1 保存时

保存必须拒绝：

- 未知字段、未知节点类型、未知端口；
- 输入端口契约与边的端口不一致；
- 单输入的多个有效来源；
- 数据类型不兼容且无正式转换；
- 未配置批处理语义的 `collection → single` 连接；
- 结构环和不合法的开始节点；
- 无效 JSON、无效变量引用。

保存可以警告但不拒绝：未消费输出、可选输入未设置、未连接的失败分支、无业务节点的草稿。

### 10.2 发布时

发布必须额外验证：

- 所有启用且必填的输入已满足；
- 所有节点存在执行器；
- 副作用节点具备执行身份与权限；
- 并发、超时和处理数量处于平台上限内；
- 写操作的重试策略符合节点幂等要求；
- 批处理异常策略完整，或用户明确接受部分失败。

错误文案必须包含：节点名称、端口名称、当前来源、期望类型和可执行的修复建议。

## 11. 标准示例：待办工单自动处理

```text
查找待办需求
  需求列表（collection<issue>）
       │
       ▼ 自动批处理：逐条、串行、失败记录并继续
  当前项（single<issue>）
       │
       ▼
准备工单上下文
  Markdown 上下文（single<markdown>）
       │
       ▼
AI 分析工单
  分析结果（single<markdown>）
       │
       ▼
记录处理结果（真实写入；需执行确认）

批处理.failedItems ──→ 创建异常工单 / 通知负责人
批处理.summary     ──→ 结束节点 / 汇总通知
```

如果“查找待办需求”已返回完整工单对象，应直接进入“准备工单上下文”。只有查询结果字段不足时，才从当前项投影 `id` 或 `key` 到“获取需求”节点读取详情。

## 12. 节点开发检查清单

新节点合入前必须回答：

- 输入是否区分必填、可选、默认、条件启用？
- 每个输入的数据类型、基数和语义类型是否明确？
- 每个输出是否明确何时产生、是否敏感、是否可能很大？
- 节点是否安全重试？若是，幂等键或去重策略是什么？
- 单节点试运行是安全、需确认还是仅模拟？
- 数组输入是整批消费还是逐条消费？
- 失败时能提供哪些结构化错误与可恢复信息？
- 是否定义了最小日志摘要而非直接记录完整敏感数据？
- 前端端口、后端契约、执行器和模板是否由同一测试覆盖？

任何一项没有明确答案，节点不得标记为可用于内置模板。

## 13. 验收标准

以下场景必须通过端到端测试：

1. 数组输出连接到单条输入时，用户能一键创建批处理段。
2. 批处理 20 项时，能显示逐项进度、成功/失败/跳过统计和每项日志。
3. 可配置读取节点指数退避重试，且写节点在未声明幂等前不能自动重试。
4. 失败项能流入异常分支，并可在死信列表单独重投。
5. 条件禁用的必填输入不阻止运行；启用后立即成为必填。
6. 未消费输出被提示但不阻止保存；无效端口/未知字段被明确拒绝。
7. 节点测试正确区分真实执行、确认执行和模拟执行。
8. 刷新、发布、执行历史回放后，端口绑定、批处理策略和日志血缘保持一致。
