## 今天可能遇到的情况（随机选一种开始）

**情况 A**：有几个工单进入 Testing 状态，需要去验证  
**情况 B**：发现了一个 Bug，但不知道能不能自己提工单  
**情况 C**：想看看当前有多少 Bug 还没修，按优先级看一下  
**情况 D**：某个之前打回的工单，开发说修好了，再测一遍  
**情况 E**：Sprint 快结束了，想确认一下哪些应该测的工单还没进入 Testing

## 操作流程

**第一步：打开系统，找今天要测的工单**

1. 访问 http://localhost:3000，登录
2. 找到状态是 Testing 的工单
   - 用左侧的 Saved Query 或者手动筛选
   - 有多少个？按创建时间排序，先测最老的

**第二步：认真做一个工单的验收**

打开第一个待测工单，像真正在测试一样操作：
- 读描述和验收标准，搞清楚这个工单改了什么
- 看开发人员的评论，有没有说明测试重点或注意事项
- 看附件，有没有截图或说明文档
- 看活动历史，这个工单被打回过几次？每次打回的原因是什么？
- 根据描述进行验证（在系统里实际操作对应的功能）

**测试通过：**
- 在评论里写清楚"测试通过，验证了 [具体内容]"
- 改状态为 Done
- 确认状态更新成功

**测试不通过：**
- 在评论里详细描述问题：复现步骤 + 期望结果 + 实际结果
- 如果能截图，上传截图作为附件（看看能不能上传）
- 改状态回 In Progress
- 确认状态更新成功，开发人员能看到评论

**第三步：处理情况 B——想提一个 Bug**

发现了一个 Bug，尝试自己创建工单看看系统是否允许，会发生什么：
- 找到创建工单的入口
- 尝试填写信息并提交
- 如果不能创建，在评论里把 Bug 描述清楚，让产品经理或技术负责人帮提

**第四步：浏览 Bug 看板**

筛选：类型=Bug，状态≠Done
- 按优先级降序看一眼，Critical/High 的 Bug 有几个
- 有没有 Bug 超期了？有没有 Bug 没有负责人？
- 随手打开一两个 Bug 工单，看看描述是否清晰，活动历史完不完整

**第五步：看 Sprint 测试进度（情况 E）**

在 Sprint 视图里：
- 哪些工单已经在 Testing 了？哪些还在 In Progress 或 Code Review？
- 距 Sprint 结束还有几天，来得及测完吗？
- 在评论里 @技术负责人，提醒有哪些工单需要加快推进

**第六步：随手记录遇到的问题**

操作过程中遇到任何不对劲都记下来，比如：
- 找不到"待我测试"的工单列表入口
- 状态改为 Done 之后页面没更新
- 想上传附件但找不到上传按钮或上传失败
- 评论发出去之后格式乱掉
- 某个工单打开很慢或者直接报错
- 活动历史显示的信息不完整或者显示乱码
- 界面某处按钮或文字看起来很奇怪
- 测试人员看到了不该看到的操作按钮（比如编辑工单内容）
